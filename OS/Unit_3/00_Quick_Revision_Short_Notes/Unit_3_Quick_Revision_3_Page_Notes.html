1. Process Concepts & Virtual Address Space

Program vs Process

• Program: Passive entity; static machine binary code on disk.
• Process: Active entity; Program in execution in RAM with PCB & registers.
• CPU-I/O Burst: Execution alternates: Compute (CPU) ↔ Wait (I/O).

Process Address Space Layout

• Text: Compiled instructions (Read-Only).
• Data: Global/static variables (.data init, .bss uninit).
• Heap: Dynamic runtime memory (malloc, new) → Grows UP.
• Stack: Local vars, activation frames → Grows DOWN.
2. Process States & PCB (Process Control Block)

5 & 7 States Life Cycle Model

• NEW → READY: Admitted by Long-Term Scheduler (LTS).
• READY → RUNNING: Dispatched by Short-Term Scheduler (STS).
• RUNNING → READY: Preempted via timer interrupt/quantum.
• RUNNING → WAITING: I/O request or event wait syscall.
• WAITING → READY: I/O completion interrupt.
• SUSPENDED (Ready/Blocked): Swapped to disk by MTS.

PCB Fields (task_struct in Linux)

• PID / PPID: Unique integer process / parent ID.
• Process State: Running, Interruptible, Zombie.
• Program Counter (PC): Next instruction memory pointer.
• CPU Registers: Saved hardware context on preemption.
• Scheduling Info: Priority, nice value, queue pointers.
• Memory & I/O: Page tables, limits, open file descriptors.

4. Threads & Multithreading Models

Thread Components

Shared: Code, Data, Heap, Open files, OS signals.
Private: Thread ID (TID), PC, Registers, Call Stack.

ULT vs KLT

ULT: Fast user-space switch, 1 block blocks all, no multicore.
KLT: Kernel managed, true multicore, independent blocking.

Thread Models

• M:1: User library, low kernel cost.
• 1:1: High concurrency (Linux/Win).
• M:N: Hybrid multiplexing (Go).

1. FCFS & The Convoy Effect
• Mechanism: Simple FIFO queue. Non-preemptive. Jo pehle arrive hua, wo pehle run karega.
• Convoy Effect: Ek bada CPU-bound process running rehta hai aur kayi chhote I/O-bound processes queue me block rehte hain. I/O devices idle rehte hain aur Avg WT drastically badh jata hai.
• Numerical Proof: P1(24), P2(3), P3(3) → Order P1,P2,P3 gives Avg WT = 17.0 ms vs Order P2,P3,P1 gives Avg WT = 3.0 ms (82.3% faster!).
2. SJF (Non-Preemptive) & SRTF (Preemptive SJF)

SJF (Shortest Job First)

• Optimality: Provably optimal for minimum Avg WT.
• Limitation: Future burst time unknown in advance. Long jobs face Starvation.
Exponential Smoothing: τ_{n+1} = α*t_n + (1-α)*τ_n

SRTF (Shortest Remaining Time First)

• Preemption: Naye process ke arrival par Remaining Time compare hota hai. If BT_new < Rem_curr → Preempt!
• Characteristics: Even lower Avg WT than SJF. Frequent context switches increase CPU switching overhead.
3. Priority Scheduling & Aging Technique

Priority Scheduling

• Convention: Typically Smaller Integer = Higher Priority (0 = Top).
• Preemptive vs Non-Preemptive: Higher priority incoming preempts running.
• Starvation: Continuous stream of high priority jobs denies CPU to low priority.

Aging Technique

• Solution: Gradually increases priority of waiting processes as time progresses.
• Formula / Rule: Increase priority by 1 every Δt (e.g. 15 mins).
• Guaranteed prevention of indefinite blocking.
4. Round Robin (RR) & Quantum Sizing Dynamics
• Mechanism: Ready Queue is Circular FIFO. Har process ko Time Quantum 'q' milta hai. Quantum khatam hote hi timer interrupt process ko tail par bhej deta hai.
• q → ∞ (Very Large): Degenerates into FCFS (Convoy effect returns; poor interactive response).
• q → 0 (Very Small): Processor sharing, but massive Context Switch Overhead thrashing.
• 80% Rule of Thumb: At least 80% of CPU bursts should be shorter than time quantum 'q'. Typical: 10ms - 100ms.

6. Multilevel Queues & Multiprocessor Scheduling

MLQ vs MLFQ

• MLQ: Static queue partitions (System, Interactive, Batch). No movement. High starvation risk.
• MLFQ: Dynamic movement. Jobs demoted on quantum expiry, promoted via Aging. Self-tuning!

Multiprocessor & SMP

• SMP: Peers, self-scheduling, per-core queues.
• Processor Affinity: Process stays on same CPU for warm cache (L1/L2 hits).
• Load Balancing: Push & Pull migration across cores.

1. Deadlock Definition & The 4 Necessary Coffman Conditions
• Definition: Permanent blocking of a set of processes where each holds a resource and waits for another.
• Deadlock occurs IF AND ONLY IF all 4 conditions hold simultaneously:
1. Mutual Exclusion: At least 1 non-shareable resource. Only 1 process at a time can use.
2. Hold and Wait: Process holds 1+ resources while waiting to acquire additional held resources.
3. No Preemption: Resources cannot be forcibly revoked; released only voluntarily.
4. Circular Wait: Closed cyclic dependency chain: P0 → P1 → P2 → ... → Pn → P0.
2. Resource Allocation Graph (RAG) & Cycle Rules

RAG Components

• Vertices: Processes P (Circles), Resources R (Rectangles with dots).
• Request Edge: Pi → Rj (Process waits for resource).
• Assignment Edge: Rj → Pi (Resource allocated to process).

Golden Cycle Theorems

• NO Cycle: 100% Guaranteed NO DEADLOCK.
• Single-Instance + Cycle: GUARANTEED DEADLOCK.
• Multi-Instance + Cycle: MAY OR MAY NOT have deadlock (External processes can break cycle!).
3. Deadlock Handling Strategies & Prevention
StrategyMethodologyCore Technique
1. IgnoranceOstrich Algorithm (Ignore it)Used by Linux, Windows (Deadlocks assumed rare; avoidance too costly).
2. PreventionInvalidate at least 1 Coffman conditionHavender's Protocol: Strict linear ordering F: R → N. Request only if F(Ri) < F(Rj). Cycles mathematically impossible!
3. AvoidanceDynamic safe-state checkingBanker's Algorithm: System never enters Unsafe state.
4. DetectionPeriodic graph analysis & recoveryWait-For Graph (WFG) cycle detection O(V^2) + Process Abort / Preemption.
4. Deadlock Avoidance: Banker's Algorithm Masterclass
Core Matrix Formula: Need[i][j] = Max[i][j] - Allocation[i][j]
• Safety Algorithm Steps:
1. Set Work = Available and Finish[i] = False for all i.
2. Find process Pi where Finish[i] == False AND Need_i ≤ Work. If none found → Step 4.
3. Work = Work + Allocation_i, Finish[i] = True. Repeat Step 2.
4. If all Finish[i] == True → SAFE STATE! Safe Sequence exists.
• Resource Request Algorithm: 1) Req ≤ Need; 2) Req ≤ Available; 3) Pretend allocate & run Safety check.
5. Deadlock Detection & Recovery Protocols

Detection & Wait-For Graph (WFG)

• Single instance resources: Collapse resource nodes → WFG.
• Cycle detection via DFS in O(V^2) time indicates deadlock.
• Multiple instance: Detection matrix algorithm using Request matrix.

Recovery Mechanisms

• Process Abort: Abort all vs Abort one-by-one by cost.
• Resource Preemption: Pick victim, Rollback to checkpoint.
• Starvation Fix: Include rollback count in victim cost.
